# Database Engineering

## Database Design & Data Modeling

- Start from business entities, relationships, and access patterns; produce
  conceptual → logical → physical models.
- OLTP: normalized (3NF), narrow transactions, many small indexed lookups.
- DW / reporting: dimensional models (star/snowflake), fact tables partitioned
  by date, slowly changing dimensions (SCD Type 1/2).
- Choose datatypes precisely: `NUMBER(p,s)`, `DATE` vs. `TIMESTAMP [WITH TIME ZONE]`,
  `VARCHAR2(n CHAR)` for multi-byte data, `CLOB`/`BLOB` for large objects,
  never store dates or numbers in strings.
- Surrogate keys (identity/sequence) for stability plus unique constraints on
  natural/business keys.
- Plan for growth: partitioning keys, archival, auditing columns
  (`created_by`, `created_at`, `updated_by`, `updated_at`).

## Normalization

| Form | Rule | Violation example |
|------|------|-------------------|
| 1NF | Atomic values, no repeating groups | `phone_numbers = '111,222'` |
| 2NF | No partial dependency on a composite key | `order_items(order_id, product_id, product_name)` |
| 3NF | No transitive dependency | `employees(dept_id, dept_name)` |
| BCNF | Every determinant is a candidate key | Overlapping candidate keys |

Denormalize deliberately (summary columns, MVs, reporting tables) only when a
measured performance need exists, and document how consistency is maintained.

## Constraints & Referential Integrity

```sql
CREATE TABLE orders (
    order_id     NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY,
    customer_id  NUMBER        NOT NULL,
    order_no     VARCHAR2(20)  NOT NULL,
    status       VARCHAR2(20)  DEFAULT 'NEW' NOT NULL,
    order_date   DATE          DEFAULT SYSDATE NOT NULL,
    total        NUMBER(12,2)  DEFAULT 0 NOT NULL,
    CONSTRAINT pk_orders         PRIMARY KEY (order_id),
    CONSTRAINT uk_orders_no      UNIQUE (order_no),
    CONSTRAINT fk_orders_cust    FOREIGN KEY (customer_id)
                                 REFERENCES customers (customer_id),
    CONSTRAINT ck_orders_status  CHECK (status IN ('NEW', 'PAID', 'SHIPPED', 'CLOSED')),
    CONSTRAINT ck_orders_total   CHECK (total >= 0)
);

CREATE INDEX ix_orders_customer ON orders (customer_id);   -- index every FK
```

- Constraints are the cheapest, most reliable data validation — and they give
  the optimizer information (join elimination, `NOT NULL` enabling index use).
- FK options: `ON DELETE CASCADE`, `ON DELETE SET NULL`, or default restrict.
- `DEFERRABLE INITIALLY DEFERRED` for circular references / batch loads checked
  at commit.
- Loading large data: `ENABLE NOVALIDATE` then `VALIDATE` later; or
  `EXCEPTIONS INTO` to find violating rows.
- Name constraints explicitly — `SYS_C00123` in an error message helps no one.

## Transactions

- A transaction starts with the first DML and ends with `COMMIT`/`ROLLBACK`
  (DDL commits implicitly — before and after).
- ACID; Oracle's default isolation is `READ COMMITTED` with statement-level read
  consistency; `SERIALIZABLE` gives transaction-level consistency (ORA-08177 on conflict).
- `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` for partial undo.
- Commit at the end of the logical business transaction — not inside loops, and
  generally not inside reusable procedures (let the caller control the transaction).
- Committing across a fetch on the same table risks **ORA-01555** (snapshot too old).

## Locking & Concurrency

- Readers never block writers, writers never block readers (multi-version
  read consistency via undo). Writers block writers on the same row.
- Row locks (TX) are stored in the block, no lock escalation.
- Table locks (TM) — unindexed FKs cause share locks on the child table during
  parent DELETE/key UPDATE.

```sql
-- Pessimistic locking with fail-fast
SELECT * FROM accounts WHERE account_id = :id FOR UPDATE NOWAIT;      -- ORA-00054 if locked

-- Queue processing with many workers
SELECT job_id FROM job_queue
WHERE  status = 'READY'
ORDER  BY priority
FETCH  FIRST 10 ROWS ONLY
FOR UPDATE SKIP LOCKED;

-- Optimistic locking: version column
UPDATE accounts
SET    balance = :new_balance, version = version + 1
WHERE  account_id = :id AND version = :expected_version;
-- SQL%ROWCOUNT = 0 → someone else changed it; reload and retry
```

**Deadlocks (ORA-00060)**: Oracle detects them and rolls back one statement.
Root cause is inconsistent lock ordering — always lock resources in the same
order (e.g. by primary key), keep transactions short, and index FKs. The
trace file in the alert log shows the deadlock graph.

```sql
-- Who is blocking whom
SELECT s.sid, s.serial#, s.username, s.blocking_session, s.event,
       s.seconds_in_wait, s.sql_id, o.object_name
FROM   v$session s
       LEFT JOIN dba_objects o ON o.object_id = s.row_wait_obj#
WHERE  s.blocking_session IS NOT NULL;
```

## Views

```sql
CREATE OR REPLACE VIEW v_active_customers AS
SELECT customer_id, name, email
FROM   customers
WHERE  status = 'ACTIVE'
WITH CHECK OPTION CONSTRAINT ck_v_active_customers;
```

- Use for abstraction, security (column/row restriction), and simplifying
  complex joins. `WITH READ ONLY` prevents DML.
- Avoid deep view-on-view stacks — they obscure plans and block view merging.
- `INSTEAD OF` triggers make complex views updatable.

## Materialized Views

```sql
CREATE MATERIALIZED VIEW LOG ON sales
    WITH ROWID, SEQUENCE (region, sale_date, amount) INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW mv_sales_daily
    BUILD IMMEDIATE
    REFRESH FAST ON COMMIT
    ENABLE QUERY REWRITE
AS
SELECT region, TRUNC(sale_date) AS sale_day,
       SUM(amount) AS total_amount, COUNT(amount) AS cnt_amount, COUNT(*) AS cnt
FROM   sales
GROUP  BY region, TRUNC(sale_date);

-- On-demand refresh
EXEC DBMS_MVIEW.REFRESH('MV_SALES_DAILY', method => '?', atomic_refresh => FALSE);
```

- Refresh: `COMPLETE`, `FAST` (needs MV logs and restrictions — check with
  `DBMS_MVIEW.EXPLAIN_MVIEW`), `FORCE`; timing `ON COMMIT`, `ON DEMAND`, or scheduled.
- `ON COMMIT` adds overhead to every source transaction — avoid on busy OLTP tables.
- `atomic_refresh => FALSE` uses truncate + direct-path insert for faster
  complete refresh (MV briefly empty).
- Real-time MVs (12.2+, `ENABLE ON QUERY COMPUTATION`) combine stale MV + logs.

## Sequences & Identity Columns

```sql
CREATE SEQUENCE order_seq START WITH 1 INCREMENT BY 1 CACHE 1000 NOORDER;

-- 12c+
CREATE TABLE invoices (
    invoice_id NUMBER GENERATED ALWAYS AS IDENTITY (CACHE 1000),
    ...
);

-- Or sequence as a column default (12c+)
ALTER TABLE orders MODIFY order_id DEFAULT order_seq.NEXTVAL;
```

- Sequences are not gap-free (rollbacks, cache loss on restart). If the business
  requires gap-free numbering, use a serialized counter table — and accept the
  concurrency cost.
- Larger `CACHE` reduces contention (especially on RAC — use `NOORDER`);
  scalable sequences (18c+, `SCALE`) avoid index right-hand hot spots.
- Reset after data migration: `ALTER SEQUENCE ... RESTART START WITH n` (18c+).

## Database Security & Privileges

- **Least privilege**: application connects as a user with only `EXECUTE` on
  API packages (and `SELECT` where needed) — not as the schema owner.
- Schema-owner pattern: owner schema holds objects (locked, no direct login),
  app user receives grants via roles; use synonyms or `ALTER SESSION SET CURRENT_SCHEMA`.
- System vs. object privileges; roles; `WITH GRANT OPTION` / `WITH ADMIN OPTION`
  used sparingly; review `DBA_SYS_PRIVS`, `DBA_TAB_PRIVS`, `DBA_ROLE_PRIVS`.
- Definer's rights vs. invoker's rights (`AUTHID CURRENT_USER`); code-based
  access control (granting roles to packages, 12c+).
- SQL injection prevention: bind variables, `DBMS_ASSERT` for identifiers.
- Row-level security: Virtual Private Database (`DBMS_RLS`), Real Application
  Security; column protection: Data Redaction, TDE for encryption at rest.
- Auditing: Unified Auditing policies (12c+); never store passwords in tables
  or code — use wallets / secure external password store.

```sql
CREATE ROLE app_rw_role;
GRANT EXECUTE ON order_api TO app_rw_role;
GRANT SELECT  ON v_active_customers TO app_rw_role;
GRANT app_rw_role TO app_user;
```
